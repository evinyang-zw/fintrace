## 3. holdout 的两次运行（一次作废）

| 轮次 | tag | 正确率 | 数值准确率 | 结论 |
|---|---|---|---|---|
| 第一次 | `v1.0-final` | 100% | **40%** | **作废**：判分器 bug，不是模型问题 |
| 官方 | `v1.0.1` | 95.0% | 100% | 计入终版 |

第一次的 3 道"数值错误"（h-c2-001 / 003 / 004）答案分别是 0.63 / 0.39 / 0.25，都是题目要求的两位小数；
判分器的 0.5% 相对容差把小比率舍入判错（0.25 vs 0.25357 差 1.4%）。

处理：修改 `eval/graders.py`，按题目要求的小数位给绝对容差（两位小数比率 → 0.005；一位小数百分比 → 0.001 不变）
并加单测；**agent 代码一行未动**（v1.0-final → v1.0.1 的 diff 只有 graders + 测试）。
第一次 holdout 按纪律作废，重跑一次，两轮都写进 `docs/evaluation-report.md` §4。

这件事本身就是 W6 最好的注脚：**holdout 不只测模型，也测尺子。**

## 4. Langfuse Input 空值：根因与修复

现象：Langfuse Cloud 上 `fintrace.run` 的所有记录 **Input 为空、Output 有值**。

排查过程（只读）：

1. 在**线上容器**里用生产 key 查 v5 observations API：`input=None`、`output="..."`，且 span 有一个
   **合成父节点**（`parent_observation_id` 存在）——确认数据确实丢了，不是看错面板。
2. 本地用 SDK 5.2.0 复现：同样的 `trace_context + input + update` 代码，**input 属性存在**。
3. 于是排除了 SDK/序列化，回到调用方——找到根因：

```python
# api/worker.py (W5)
async def _finish(self, run_id, answer):
    self._trace(run_id, answer, payload, usage, "done", None)  # ← 传了 Answer


# _trace 里：
question = getattr(question_or_answer, "question", "") or ""  # Answer 没有 .question
```

成功路径把 **Answer** 当成"question_or_answer"传进去，`getattr` 取不到 question，input 变成空字符串。
失败路径传的是 Question，所以只有成功记录缺 Input——与现象完全吻合。

修复：`_finish(run_id, question, answer)` 显式传 Question；加两层离线回归测试：
`tests/test_worker_trace.py`（caller 把 Question 传给 tracer）+ `tests/test_observability.py`（tracer→SDK 的 `input`/`output` 契约，无网络）。

**线上验证（2026-11-14 22:5x）**：release 部署 `d3cd070` 后，用生产 token 发一条真实问题
（run `1a427dea-6885-4f91-98b4-843e260cb0b4`），从容器内查 Langfuse observations：

```
input = '苹果 FY2024 的总净营收是多少美元？'
output = '苹果 FY2024（2023-10-01 至 2024-09-28）的总净营收为 391,035,000,000 美元 …'
```

Input 已有值，修复在线上生效。

同时补了两个工具层 bug（也是 W6 新增题暴露的）：

- `xbrl_fact` 的财年元数据取自"最后一次出现该事实的 filing"，10-Q 里的年度比较数会被标成 Q3，
  模型因此拒答。改为按事实自身的 period 长度判定 FY，并输出 `period_start`。
- `gross margin` / `operating margin` / `net margin` / `r&d` 没进别名词典，导致既有的 `c1-004` 偶发误拒。
