# 简历 bullet（W3 收尾版）

> 数字来自 W3.1 的 45 题评测；每条都可指向仓库里的报告或代码。

- **从零构建可审计的美股财报 Agent**：10 家公司 / 85k XBRL facts / 45 题金标；
  自建三档检索（BM25、多语 dense、RRF 融合、cross-encoder 重排），多跳题 recall@8
  从 80% 提升到 100%。
- **用 trace 定位真正的瓶颈**：端到端正确率不涨，不是召回问题，而是 Agent 只读 400 字
  摘要就拒答；改为查询聚焦摘要 + 强制 `get_section` 后，多跳题从约 50% 到 100%，
  总体正确率 77.5% → 95.0%（配对 +17.5pt，95% CI [+5.0, +32.5]）。
- **设计 claim 级引用校验**：数字引用 XBRL fact 做确定性复算，正文引用用 LLM 判
  entailment；判官用 60 条盲标校准，二次加权 κ = 0.795（完全一致 90%）。
- **把 ReAct 循环迁到 LangGraph 状态机**：Postgres checkpointer + `interrupt()` 人工放行，
  `kill -9` 后换进程恢复同一 thread；新增 verify/repair 节点做生成时校验，
  引用支撑率 +3.5pt，50 题 × 4 seed 与手写版打平（95.0% vs 95.0%，配对 CI [-3.3, +3.9]）。
- **工具层 MCP 化**：4 个工具独立进程、只读 DB、5s 超时、8 条契约测试；客户端分配句柄，
  服务端保持无状态。工具描述实验：现行描述 17/20 vs 极简描述 15/20。
- **工程化**：173 个测试、覆盖率 75.6%、mypy strict、CI 不依赖网络；单题成本 ~$0.0006；
  LLM 尾延迟用连接池 + 对冲请求治理（注入 10s 慢调用从 10.0s 降到 1.0s）。

## 面试时的三个追问

- **为什么数字不经过 LLM？** XBRL fact 是权威来源；LLM 只负责选事实和措辞，
  校验器拿 claim 里的数字和 fact 值做相对误差比对。
- **为什么 rerank 只排序不筛选？** 20→8 的筛选会让约 13% 的多跳题丢掉正确章节；
  先保 recall，再谈排序。
- **判官凭什么可信？** 60 条盲标、人标不动、只改规则；κ 从 0.603 到 0.795，
  剩余分歧逐条列出，不为它们继续调 prompt。
- **用 LangGraph 买到了什么？** 不是更短的代码（图版多约 500 行），是跨进程恢复、
  可中断的人审、生成时校验；A/B 证明换了编排不掉分。
