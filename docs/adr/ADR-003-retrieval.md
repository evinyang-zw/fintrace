# ADR-003：检索用精确扫描、RRF 与可选重排

- 状态：已接受（W3）
- 日期：2026-10-30

## 背景

W2 的检索只有 BM25，F2 多跳 5 题实质 0/5：中文问题被模型翻成英文关键词，BM25 对措辞敏感，
叙述类段落召回不到。W3 要加多语 dense 检索并做消融，但必须先决定三件事：索引怎么建、
多路结果怎么合、重排放哪一层。

## 决策

1. **不建 HNSW，用精确扫描。** 2 万个 chunk、1024 维，带公司与时点过滤的全表扫描是毫秒级。
2. **混合用 RRF（k=60），最终条数固定 8。** 所有档位输出同样多的上下文，比较才成立。
3. **重排只改顺序，不做筛选**：对融合后的 top-k 重排，不把 20 个候选砍成 8 个（W3 实测 20→8 会让约 13% 的 F2 题丢掉正确章节）。
4. **向量单独一张表**（`chunk_vectors`，主键 `chunk_id + model`），不塞进 `chunks`。
5. **缺 key / 缺向量 / 重排失败时显式降级**，降级原因写进工具返回、trace 和报告。

## 理由

**为什么不建 HNSW。** 近似索引在带过滤条件时召回率会悄悄下降，还要多调一个 `ef_search`；
20k 规模下它换来的只是毫秒，而项目最贵的东西是"检索到底召回了没有"这个结论的可信度。
等 chunk 过十万再谈索引——写在这里，是为了避免以后有人"顺手优化"。

**为什么 RRF 而不是加权分数。** BM25 的 `ts_rank_cd` 与余弦相似度量纲不同，归一化会引入
一个需要调的参数；RRF 只用排名，免调参，且对单路失效（比如 BM25 对中文查询返回空）不敏感。

**为什么固定 k=8。** 初版计划写"重排后 top-5"，会让上下文长度和成本一起变，A1 与 A2 的差异
就说不清是"排序更好"还是"看得更少"。最终条数固定，重排只负责把对的段落排前面。

**为什么向量要带模型名。** 换 embedding 供应商时，旧向量若混进新查询，结果不会报错，只会
变差——这是最难查的一类 bug。主键带 `model`，查询显式过滤，换模型只需重新回填。

## 后果

- 检索延迟主要花在 embedding 请求上（每 query 一次，进程内缓存重复 query）；
- 没有向量时 `hybrid` 会降级成 BM25，报告里能看到 `degraded=[no_embedding_key]`，
  消融表必须把这类 run 标出来，不能当作 hybrid 的结果；
- 更换 embedding 模型需要 `make embed` 重跑（2 万条，一次性）。
