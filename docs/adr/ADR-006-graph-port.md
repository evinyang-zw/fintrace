# ADR-006：把 ReAct 循环装进图，而不是重写成分步流水线

- 状态：已接受（W4）
- 日期：2026-11-11
- 关联：ADR-002（手写 ReAct）、主设计 §3 架构图 / §9 M3

## 背景

W3 结束时 hybrid 档在 45 题上已经到 95–97.5%，F2 14/15，p95 约 9 秒。
W4 的任务是补上 LangGraph 状态机、checkpoint、interrupt 和校验回环。

主设计的架构图画的是 `plan → retrieve → extract → compute → draft → verify`。
照字面实现，等于把"模型自己决定下一步查什么"换成固定流程。

## 决策

1. **内层忠实移植**：`agent → tools → agent` 的条件循环原样保留，提示词不变，
   工具协议不变。图只是把这套循环显式化，不是重新设计推理。
2. **外层新增**：`verify → repair → review → finalize`，这是 W4 真正的新东西。
3. **扁平图，不拆子图**：只有一个流程，子图只增加 state 映射成本。
4. **状态必须可序列化**：句柄存成记录，节点里重建 `EvidenceStore`；
   任何客户端、连接、内存对象都不进 state。
5. **Postgres checkpointer**：`thread_id = trace_id`，跨进程恢复是硬验收。

## 理由

W3 的证据很直接：检索 recall 修好后端到端不动，真正起作用的是"摘要不够就打开章节"这个
**工具使用策略**。固定流水线会把这种自适应行为挤掉。相比之下，`verify/repair` 是对**已有
答案**的后置约束，不会改变模型怎么找证据——这是低风险、高价值的加法。

扁平图的理由同样实际：拆子图会让 checkpoint 里的 state 命名空间变复杂，而 W4 只有一个流程。
等 W5 出现"研究 / 校验 / 发布"多条流程时再拆，才有复用价值。

## 代价（实测）

- **多一次校验调用**：引用检查从判官阶段前移进循环，单题成本从 $0.0006 升到约 $0.0010。
- **状态序列化有约束**：`EvidenceStore` 不能直接放进 checkpoint，必须先转记录。
- **HITL 会挂住评测**：`REVIEW_MODE=never` 是评测默认值，否则 50 题会停在第一道 interrupt。

## 被否决的方案

| 方案 | 为什么不用 |
|---|---|
| 按架构图重写成分步流水线 | 丢掉 W3 验证过的自适应工具使用，预期回退 |
| 直接用 `create_react_agent` | 失去对预算、重复调用、JSON 修复的控制，且无法与 W2 基线逐项对比 |
| MemorySaver | 只能同进程恢复，验收要求 `kill -9` 后恢复 |
| 子图拆分 | 单流程无复用收益，调试成本更高 |
