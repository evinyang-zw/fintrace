# ADR-002：手写 ReAct，而不是直接上框架

- 状态：已接受（W4 复盘）
- 日期：2026-10-29

## 背景

W2 需要一个能跑、能量、能解释的 Agent。最省事的做法是 `pip install langgraph`，照文档拼一个
`create_react_agent`；但那样一来，"Agent 到底怎么做决策"会变成一个黑盒，W4 换框架时也说不清
到底换来了什么。

## 决策

1. **自己写循环**：状态、步数上限、预算守卫、重复调用检测、解析修复，全部显式。
2. **动作协议用 JSON**，不用经典 ReAct 的 `Thought/Action/Action Input` 文本格式。
3. **工具只给四个**（`search_filings` / `get_section` / `xbrl_fact` / `compute`），不追求覆盖。
4. **引用只能用工具返回的句柄**（`K1..Kn`），模型不得自己拼 accession。

## 理由

**JSON 而不是文本协议。** 经典格式在中文、多行、带引号的参数上极容易解析失败；JSON 可以
schema 校验、可以回放、可以明确区分"模型没想清楚"和"模型格式写错"。代价是模型偶尔会
在 JSON 前后加解释文字——30 次运行里出现 2 次，都靠一次修复提示拉回来了。

**四个工具。** 工具越多，选择错误率越高。W2 的观察：模型几乎不会用错工具，但会用错参数
（中文 query、猜错的 `period_end`），所以本周的返工都在参数契约上，而不是工具数量上。

**句柄而不是自由引用。** 如果让模型自己写 `(accession, item, char_start, char_end)`，它一定
会编。句柄把"引用哪段"变成选择题而不是填空题，判官才有东西可查（span 是否存在、是否在
本次 evidence 里、引文是否匹配）。

## 代价（实测）

- **多一步翻译**：中文问题要模型自己翻成英文关键词，因为语料是英文、检索是 BM25。
  这既多花一步，也给 W3 的检索消融埋了一个混杂变量（换多语 embedding 后不再需要翻译）。
- **没有并行工具调用**：一次只能调一个，多跳问题被拉长。
- **没有 checkpoint**：超时或崩溃就重跑，不能从中间恢复（W4 的 LangGraph 才解决）。
- **`max_steps=7` 是拍的**：30 次运行里 2 次撞上限，平均 4.5 步。W3 扩题后要重估。

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 直接 `create_react_agent` | 学不到终止条件、预算、错误语义；W4 的框架对比会变成"两个黑盒比" |
| 纯文本 ReAct 协议 | 解析脆弱，且无法做结构化校验 |
| 计划-执行两段式（先规划再执行） | W2 只需要基线，规划器是 W3 的检索分解才需要 |
| 多个专职 Agent（CrewAI 式） | 单任务场景下是过度设计，且不可控变量更多 |

## 后续（W4 必须回答）

换 LangGraph 时，用同一批题对比：代码行数、成功率、平均步数、单题成本、调试时间。
如果框架没在这五项上赢，就不换——ADR 要能承受"不换"的结论。

## 证据

- `agent/react.py`：约 330 行，含全部防呆。
- `data/traces/`：每次运行完整落盘，可逐题回放。
- 30 次基线运行：平均 4.5 步、2 次撞上限、2 次解析失败（均修复成功）。
