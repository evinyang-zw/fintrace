# ADR-001：为什么第一周不写 Agent

- 状态：已接受
- 日期：2026-10-27

## 背景

W1 的直觉做法是先做出一个能回答问题的 Agent，再补评测。绝大多数作品集就是这么做的，
结果是 README 里写"效果不错"，但没有任何分母。

## 决策

W1 只做两件事：**能喂的数据**（摄取管道）和**能打分的尺子**（评测协议、指标、报告）。
唯一的 Agent 是 `NullAgent`——它对所有问题都回答"无法确认"。

## 理由

1. **没有基线，就没有"改进"**。W2 的手写 ReAct 版需要和某个东西比，否则"调了三天变好了"
   只是一种感觉。
2. **尺子本身需要校准**。NullAgent 的输出是可预测的：正确率 0、引用支撑率 0、误拒率 100%。
   如果报告不是这三个数，bug 一定在 `eval/` 而不是在 Agent。
3. **评测协议是唯一不能返工的接口**。`Answer{text, citations, refused, usage, trace_id}`
   定错，后面每换一次 Agent 实现就要改一次评测代码。
4. **招聘方看的是判断力**。先建尺子再优化，是一个能在面试里讲五分钟的决策；
   "我用了 LangChain"不是。

## 代价

- W1 结束时没有一个能演示的问答界面（W2 才有）。
- 30 道题要在没有 Agent 的情况下人工出完并核对数字，枯燥且容易出错
  ——所以加了 `make q-check` 的数值对账。

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 先写 Agent，跑通再补评测 | 会针对"能跑通的几个例子"调优，评测集失去独立性 |
| 直接用 Ragas / DeepEval 的现成指标 | 指标定义不透明，且无法覆盖"拒答校准"这类业务关键维度 |
| 人工看 20 条回答判断好坏 | 不可复现、不可回归，CI 里无法门禁 |
