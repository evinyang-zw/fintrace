# ADR-005：用对冲请求削掉 provider 的尾延迟

- 状态：已接受（W3.1）
- 日期：2026-11-01

## 背景

935 次 LLM 调用的分布是双峰的：p50 1.15s、p90 1.86s，但有 **5.7% 的调用卡在
15–19s**（p95 17.1s、p99 18.8s）。输入 token 与延迟的相关性只有 0.04；小请求并发 4 路
不触发；换连接池只省 0.2s。慢调用会在同一道题里成簇出现（7 条 trace 出现两次慢调用，
独立假设下只应有 1 条），说明是 provider 侧的窗口性抖动。

端到端 p95 因此被拉到 22–36s，而工具耗时始终 <0.5s。

## 决策

1. **连接池**：一个进程复用一个 `httpx.AsyncClient`，不再每次调用新建（省一次握手）。
2. **对冲请求**：单次调用 3.5s 未返回，就并行发出第二份完全相同的请求，取先成功的那份，
   另一份取消。**最多对冲一次**，不递归。
3. **只有慢调用付第二份钱**。`LLM_HEDGE_AFTER_S=0` 可关闭；回放模式不触发。
4. **可观测**：`LLMResult.hedged / hedge_won` 写进 trace，能算真实触发率与胜率。
5. 单次 25s 硬超时保留，作为最后兜底。

## 理由

- **超时重试不如对冲**：5s 超时会杀掉 5–6s 的正常调用；对冲保留两份，先到先得。
- **比跨供应商对冲简单**：同一模型、同一 prompt，不改变输出分布；代价只是 5.8% 的
  额外调用。跨供应商（百炼 Qwen）能抗全局慢窗口，但会让同一题混模型，留作 B 方案。
- **比模型路由对症**：p50 已经 1.2s/次，问题不在平均速度，而在 5.7% 的尖峰。

## 验证

- **确定性 bench**（`make hedge-bench`）：本地假服务让每个 prompt 的首次请求睡 10s、
  重复请求立即返回。8 次调用：未对冲 p50 10.01s，对冲后 p50 **1.00s**。
- **真实 A/B**（45 题 hybrid，各 1 次）：对冲组恰好落在无慢调用的窗口（max 9.7s，
  `hedged=0`），所以**没有观测到线上 p95 改善**；正确率 95.0% → 100.0%、成本
  $0.0005 → $0.0006 都是运行间方差，不能归因给对冲。

## 后果与限制

- 慢调用会额外产生一次请求；被取消的那份可能仍被计费，而当前成本只统计胜者，
  **报告里的成本会低估真实账单**（预计 +6% 以内，需对账单核对）。
- 若慢窗口是全局的，两份都会慢，延迟变成 `3.5s + 慢调用`，比原来更差约 3.5s；
  用 `hedge_won` 监控，连续偏低就升级到跨供应商对冲。
- 回放/离线测试不受影响：cassette 命中时不经过 HTTP 层。
